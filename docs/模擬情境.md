## 公開操作契約

透過 `GET /api/workspace?module=schedule|report|mold` 查詢 `records`、`catalogs`；可用設備、日期／區間、工單、排序與分頁條件。原資料欄位使用大寫名稱；查詢結果的衍生欄位用於人員辨識。

模型及人工表單只產生白名單業務參數，不能指定表名、SQL、URL 或 LOGIN_USER。每次寫入經草稿、明確同意與可追溯記錄，由服務層管理身分、過期、版本與冪等性。

排程 `schedule.save`：設備、品號、模具、開始時間、週期秒、目標模次、狀態及明細為必填；修改加 `schedule_id`。明細為 `{detail_id?,mold_detail_id?,part_no,wo,cavities}`。`detail_id` 是既有排程明細 SID；`mold_detail_id` 是模具明細 `TOL_DETALS_SID`，兩者不可混用。同模具同品號有多筆時，新建必須從選項明確選擇模具明細，不猜第一筆；修改指定既有排程明細時可省略並保留原關聯。不同模具明細可以使用相同品號及工單，依模具明細 SID 驗證重複。優先序預設3、備註可空。未帶時區的開始時間視為 MES 伺服器本地時間，保留原數字，08:00前歸前生產日。帶明確時區時先依 `MES_SERVER_UTC_OFFSET_HOURS` 換算，本次資料庫 GETDATE／SYSUTCDATETIME 比對為 UTC+07，因此設定預設7；不能依使用者瀏覽器時區或台灣位置猜成 UTC+08。

| 動作 | 必要參數 | 可選參數 |
|---|---|---|
| `schedule.save` | equipment、part_no、mold_no、start_time、cycle_seconds、target_shots、status、details | schedule_id、priority、comment；details 內 detail_id、mold_detail_id（歧義時必選） |
| `report.add` | execution_id、ok、defects | comment |
| `report.update` | report_id、ok、defects | comment |
| `report.delete` | report_id | 無 |
| `report.cavities` | execution_id、cavities | 無 |
| `report.complete` | schedule_id | 無 |
| `mold.mount_start` | schedule_id | 無 |
| `mold.mount_finish` | schedule_id | 無 |
| `mold.unmount_start` | schedule_id | 無 |
| `mold.unmount_finish` | schedule_id | 無 |
| `mold.clear` | schedule_id | 無 |

`defects` 為 `[{code:"NG01",quantity:2}]`；原因不得重複，數量與良品為非負整數。不良總數由原因合計，不能另外傳入不同總量。schema 可由 `/api/capabilities` 取得，所有物件拒絕額外欄位。

報工查詢每執行列附 `REPORTS`，每次報工附 `DEFECTS`；`MANUAL_OK`／`MANUAL_NG` 為人工合計，`IOT_QUANTITY` 是獨立來源，`IOT_INFERRED_OK=IOT_QUANTITY−MANUAL_NG`。IoT 未知維持 null，不混同人工良品；不把負推算值悄悄截為0。

模具查詢以排程彙整，附 `EXECUTIONS` 與 `NEXT_ACTION`。四階段時間由伺服器取得，UTC 輸入依上述 MES 時區設定換算，不接受對話自訂補登時間。上模開始同步 CHECK_IN_TIME；下模完成同步 CHECK_OUT_TIME、COMPLETED、COMPLETED_TIME；清除清空四個模具時間、進出站時間及完工時間，設 COMPLETED=N，保留原後端未清除的其他欄位。

## 查詢篩選與展示

| 條件 | 契約 |
|---|---|
| equipment／eqp_no | 設備精確相等 |
| schedule_id | 三模組皆以排程識別碼精確定位；不存在回空資料，不退回全清單 |
| execution_id | 僅報工模組，以歷程識別碼精確定位；與 schedule_id 同時指定取交集 |
| part_no | 品號精確相等；報工由對應排程明細取得，排程／模具保留含該品號明細的排程 |
| wo | 工單精確相等；排程查表身、模具查執行工單 |
| date／schedule_date | 單日或 `開始~結束`，含起訖；支援 yyyy-MM-dd、yyyy/MM/dd、八碼日期；不合法日期及逆向區間拒絕 |
| factory／fac | fac1=MC1–20、fac2=MC21–46、fac3=MC47–60；未知廠別空結果，依原前端分段 |
| mold／tol_no／mold_no | 作業列依模具編號包含、不分大小寫 |
| catalog | 指定非空值時只回選項，records 為空且 total=0；parts、molds、work_orders 皆使用同一選項關聯契約 |
| search | 在選項的品號與規格中做不分大小寫的包含搜尋，不影響作業列；不會替使用者自動選取搜尋結果 |
| completed | Y／N 精確比對 |
| sort | 逗號多欄，例如 `PRIORITY,-SCHEDULE_START_TIME`；負號或 `:desc` 降冪；數值用數值排序 |
| page／page_size | 頁碼至少1，每頁1–100，超過最後頁時收斂到末頁 |

選項查詢例如 `module=schedule&catalog=parts&search=右側` 只列出 EPS-B，不自動帶出模具與工單；明確指定 `part_no=EPS-B` 才依品號列出 MOLD-A。與正式查詢契約相同，模具保留全部明細，因此 MOLD-A 同時提供 EPS-A／EPS-B 及其工單，不把同模具的另一品號隱藏。選項的 `mold_no`／`tol_no` 另可精確指定模具，`wo` 精確縮小候選工單。未知品號、模具或搜尋詞不會退回全部相關候選。未指定選項篩選時仍保留原合成資料入口的完整小型 catalog，便於演練。

`history` 的定義：

- `all`：預設合成情境全資料檢視，便於從待執行到完工回放，並非原 MES 的目前設備看板。
- `running`：報工依實際 Grid SQL 的 COMPLETED=N 且 CHECK_IN_TIME 非空；模具以每設備最新已上模未完工排程顯示，閒置設備亦有一列，此時排程 SID 為 null，需從 CANDIDATES 明確選擇。
- `pending`：新增的便捷篩選，未上模且未完工；不是原查詢函式的名字。
- `completed`：完工資料。
- `history`／`true`：報工全歷史；模具僅已上模且排程建立時間在近3個月，依清除函式條件。隔離資料使用固定模擬日期2026-10-30判斷，避免日後開啟範例時合成歷史消失。

模具候選以排程日不早於2026-07-01、未完工、未上模為基礎，依優先序排序；日期門檻是來源函式現值，不宣稱為永久業務政策。廠別是展示篩選，不能當成權限證明。`history=history` 未填 completed 時顯示全部狀態；要重現原清除頁預設需傳 completed=N。

## 原規則與改善分界

- 原排程規則：零模穴可以無工單；有工單文字必須合法；全表至少一筆合法工單，零模穴亦計入。TRY、DO、RUN 沒有原有轉移順序。
- 原後端規則：設備須唯一且有 FAB；班別採同廠當日優先，否則通用區間；班起迄必須成對、結束晚於開始。
- 修正原缺陷：每次保存重新計算全部 TARGET_PCS，改目標模次不保留舊件數；小數、負數或非數字不悄悄截斷。
- 新防護：驗證主檔及明細歸屬、整數與合法狀態、拒絕不明參數。這些不可聲稱原控制器已有。
- 隔離模型以複製狀態計算新結果；驗證失敗不修改傳入狀態。持久化交易與確認機制由公開服務層執行。
- 原報工修改只 UPDATE 既有原因的缺陷，在模擬中改為完整保存所選原因集合，允許補新增原因；對應原本多表非交易風險，由服務層交易處理。
- 原報工模穴介面可填小數，但只讀資料庫證據為 OPI_CAV `decimal(18,0)`。新介面拒絕小數，避免隱性捨入；這是精度一致性修正，不能宣稱已重現原頁面小數寫入後的實際結果。
- 模具階段順序原由前端按鈕控制；新服務也在執行層驗證，並拒絕重複階段、先後時間矛盾及多工單狀態不一致。
- 完工保留原有同排程全部列與下一排程 REAL_CHECK_IN_TIME 的連動；下一排程仍依同設備班日未完工、CHECK_IN_TIME 排序決定，不擅自加「必須晚於目前排程」規則。新增拒絕重複完工，避免再次覆寫時間。
- 未擅自加入「完工後禁止報工增改刪」或「同機台排程不能重疊」限制，因原可見程式沒有此規則；若要加入須明確核准。

## 排程觸發器同步與資料範圍

原排程存檔 SQL 直接寫主表及明細，2026-10-30 已唯讀證實資料庫的明細 AFTER INSERT／UPDATE／DELETE 觸發器會同步 `WIP_OPI_WDOEACICO_HIST`，且歷程主鍵等於明細主鍵。完整證據見 `docs/inventory/schedule.md`。隔離模擬已依此同步：保存新排程時立即建立每筆明細的歷程，包含零模穴、空工單明細；新增歷程 SID 等於明細 SID，WO_SID=0 時 WO 為 null，尚未上模的時間仍為 null。查詢品號由排程明細衍生，不把 PART_NO 當成 HIST 的資料庫欄位。

修改排程會同步工單、設備、模具、班別、生產日與排程編輯者時間，OPI_CAV 重設為排程模穴；四個模具階段、進出站／實際進站時間及完工狀態／時間維持。刪除明細同步移除歷程。既有合成範例2001／1101等識別碼透過明細關聯保留歷程 SID，避免破壞示範中的既有報工關聯；新建資料均使用同鍵。已有人工報工的明細刪除或更換工單／品號／模具明細會拒絕，與正式 adapter 採相同新防護。首次上模不再補建歷程，缺失歷程須先修復資料。

人工報工、班別與模具主檔僅為情境所需子集，不能代表完整正式主檔。模具目前看板在同排程工單狀態一致的合成資料中彙整；真實 SQL 對混合狀態的分組與 MIN／MAX 時間仍須正式唯讀契約驗證。正式 adapter 不得直接依未核對的記憶體欄位建立 SQL。

## 驗收紀錄

驗收以公開 HTTP 為邊界，詳見 `tests/test_domain_http.py`。每一切片先觀察失敗再實作；首次入口尚未完成時出現匯入失敗，入口完成後轉為具體功能失敗與修正。2026-10-30 執行 `.venv/Scripts/python.exe -m pytest tests/test_domain_http.py -q`：59項通過；此數量僅涵蓋本檔，不代表真實模型、瀏覽器或正式資料庫測試。新增案例包含班別設定可查詢、帶時區時間依 MES 的 UTC+07 設定跨08:00計算生產日、目標件數乘積超過資料庫 `decimal(18,0)` 精度時於草稿拒絕，以及保存排程立即建立歷程、更新保留操作時間、刪除同步和已有報工保護。查詢補強的三個切片先分別觀察8項識別碼、6項品號關聯、10項選項與模具別名測試失敗，再實作至全部通過；涵蓋未知識別碼回空、交集不符回空、中文規格／品號搜尋及同模具全部明細工單保留。

已執行情境包含：跨08:00生產日且確認前不變；人工報工／IoT分離及未知；新增原因修改與硬刪；單列模穴和整排程完工連動；四階段與清除六時間；新排程修改→上模→報工→下模；不合法數字／原因／型別／偽造身分欄位；設備日期工單查詢及數值排序分頁；三廠篩選、多欄排序、模具目前看板閒置設備、歷史已上模限制；非法日期、逆向區間、極大數量與日期算術不產生500。

同品號多模具明細補驗：新增 MOLD-SPLIT 合成情境，新增／修改可分別保存左右模具明細，修改時重排資料不改原關聯；缺少明確模具明細、跨模具、品號不符、重複模具或排程明細均拒絕。品號與模具同時指定時採交集。獨立 SQL 新庫亦已通過新增與修改的公開 HTTP 測試，詳見排程盤點的補驗紀錄。
