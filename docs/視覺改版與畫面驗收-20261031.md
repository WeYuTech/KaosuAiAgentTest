## 1. 來源讀法、採用範圍與證據

### 1.1 以最終有效樣式為準

來源的 `loader.js` 依序建立 `chat.css` 與 `tailwind.css` 的 stylesheet 節點，再載入聊天程式。`tailwind.css` 由 `src/tailwind.input.css` 與 `tailwind.config.cjs` 編譯；它覆寫同一組元件的基本樣式。因此不能只讀 `chat.css`，把被覆蓋的 488×720px 浮窗、22px 圓角、灰色啟動器或舊泡泡當成最新畫面。[來源：loader][S-LOADER]、[Tailwind 原始樣式][S-INPUT]、[編譯樣式][S-COMPILED]

| 來源檔 | 本輪用途 | 不移入 Kaosu 的內容 |
|---|---|---|
| `tailwind.config.cjs` | 深藍／黃／淺灰 tokens、陰影與字體堆疊。 | 不因此安裝 Tailwind 或更換目標建置系統。 |
| `src/tailwind.input.css`、`tailwind.css` | 元件有效外觀、留白、圓角、尺寸及響應式覆寫。 | 不把兩份來源 CSS 原樣疊成 Kaosu 的第四套覆寫；映射到既有 tokens／樣式。 |
| `chat.css` | 未被覆蓋的布局、捲動、safe area、焦點、輸入最大高度與 reduced-motion。 | 不以低優先樣式蓋回 Tailwind 的最終外觀。 |
| `chat.js` 的畫面結構與資產引用 | 標頭、歡迎卡、直排範例、訊息卡、composer、歷史次級畫面的呈現關係。 | 不搬入來源 API、SSE 流程、資料狀態、ADMINV2-only 授權、localStorage TokenKey、統計功能或「每題獨立分析」語意。 |
| `loader.js` | 了解樣式載入與浮動元件的來源結構。 | 不取代目標的 `widget-loader.js`、同源 iframe／postMessage、九頁宿主入口與 MES Session 契約。 |

來源提供的是以淺色為主的聊天／查詢 widget。**未在本輪來源 UI 中找到 dark／system 主題選擇或桌面滿版切換實作**；Kaosu 已有的深色／跟隨系統、放大／還原、三語、業務卡及按需摘要，都要以新視覺語言延伸，不能聲稱來源已提供。來源的問答歷史／每日統計也不能冒稱為 Kaosu 的操作稽核。[來源：畫面結構][S-CHAT]、[來源說明][S-README]

### 1.2 本輪要解決的目標畫面問題

目前 Kaosu 的 `main.tsx:352、365、368` 有多層標頭與重複脈絡；`:372` 的 prompt 與 `:375` 的 GuidedFlow 起點並列；`:388` 的摘要又重複對象及完整 snapshot。`styles.css`、`desktop.css`、`conversation.css` 對控制項與內容寬度有交疊覆寫。這些結構問題仍要處理，但解法採本輪參考元件，不再依舊原型重新設計一個石墨色全螢幕首頁。[目標來源][T-MAIN]、[目標樣式][T-CONVERSATION]

本規格只定義待實作／待驗收要求。來源程式碼可證明樣式與結構；是否在 Kaosu 真實狀態下看起來一致且能操作，仍須以實作後的瀏覽器畫面及功能證據確認。

### 2.2 啟動器、浮窗與標頭

來源桌面啟動器是**深藍膠囊、2px 黃邊、白色圖示與文字**，最小高度 52px、水平內距 20px，靠右下並考慮 safe area。來源桌面浮窗最終上限為 `width:min(520px,calc(100vw - 48px))`、`height:min(760px,calc(100dvh - 48px))`，圓角 24px；一般右側留 28px、底部留 24px。[來源][S-INPUT-SHELL]、[未被覆蓋的定位][S-BASE]

這組幾何對齊 Kaosu **尚未展開的浮窗模式**。目標 standalone `.launcher/.assistant-panel` 與宿主 `widget-loader.js` 的 Shadow DOM／iframe 外框要同步檢查，不能只改 React 內部，外框仍停在舊白色 44px 圓鈕與 400×500px。保持現有 open／close／focus 與 iframe 訊息契約；收合後的入口清楚可到達，不額外產生另一顆啟動器。

標頭採來源的**白底品牌區＋淺灰工具群**，使用威友科技品牌資產；不自行改造 Logo。來源主標頭最小高度 82px，標題 16px，桌面 Logo 寬 112px；窄版按來源規則縮至 96／76px。這些是來源的元件尺度，不是 Kaosu 加上三語、模組與權限後的總高度上限。

Kaosu 的語言、主題、可信身分、三模組、收合／既有放大還原功能仍須可到達。可將低頻偏好放進有名稱的工具選單，將模組與必要作業脈絡放在一個緊湊工作區段；不要重建「品牌一列、身分一列、對話標題一列、空工單一列」的堆疊。狀態標籤採真實模式／身分／API 資訊，不能照抄來源 BETA 或連線點，讓使用者誤以為已連線或有寫入權限。

### 2.3 歡迎卡、直排任務入口與訊息卡

起始畫面採來源白色歡迎卡：16px 圓角、淡藍灰邊界、約 20px 內距與輕陰影；標題約 24px，窄版可 20px。內容使用 Kaosu 任務語意，不複製「每次提問獨立分析、不帶上一題」或來源固定查詢文案。

歡迎卡下方保留**唯一一組直排、滿列寬的白色任務選項**：12px 圓角、細邊界、最小高度 44px、列間距約 8px，hover 採淡黃與黃邊。常用任務可以保持三個，但不再以舊原型的三張橫排大卡為目標。排程可顯示新增／查詢／調整；報工與模具依既有能力提供對應常用入口，其餘動作在明確的「更多操作」可到達。

任務啟動後，唯一 Guide 接續選對象、填資料、核對與結果，不再平行展示第二套 prompt／action grid。啟動判斷沿用 Guide 步驟與查詢狀態，不能只看 `guide.action` 是否非空，因為唯讀 query 可保留空 action。無模型時仍能從這組入口接續人工流程。[目標 Guide][T-GUIDE]

助理訊息採來源**深藍 32px 標記＋白色圓角卡**，桌面卡片約 16px 內距；使用者訊息靠右、淡藍灰底，最寬約可用訊息區的 82%。工作卡及確認卡沿用相同表面、邊界與圓角語言；業務欄位仍綁原有狀態，不以裝飾對話文字冒充已保存。消息區桌面約 20px 內距，窄版約 16px，長識別與多明細可換行或在自身表格內捲動。[來源][S-INPUT-MESSAGES]

### 2.4 字體、密度、滿版與窄版延伸

來源使用 `Noto Sans TC / Microsoft JhengHei / Segoe UI / sans-serif`；一般訊息約 14px、行高 28px，手機約 15px；textarea 是 16px。目標可映射此字體堆疊，保留既有泰文字體及授權，不為此新增 CDN 或未核對字體來源。

**Kaosu 業務欄位值、必要錯誤及核對內容維持至少 16px**，作為現有作業可讀性的延伸；一般聊天與次要資訊可依來源層級約 14px。不能將來源 11／12px 的工具或統計輔助字直接用在工單、數量、影響與獨立同意內容。主要可操作控件至少 44px；來源送出維持 48×48px。這是本輪明確尺度，不再同時執行舊 36／40／48px 的互相覆寫規格。

來源在 600px 以下採距視窗邊緣約 12px、考慮 safe area 的近滿版卡；640／420px 規則會縮品牌、收工具文字。Kaosu 可將其圓角、間距、控制密度套用到窄版，但**保留目標既有手機全螢幕、桌面展開／還原與宿主同步能力**。來源並未提供桌面滿版切換，不能刪掉目標能力來聲稱完全照抄。[來源響應式][S-INPUT-MOBILE]、[目標宿主][T-LOADER]

滿版尺寸沿目標現有展開容器，主流程、工作卡與 composer 使用同一套可用寬度規則；摘要開啟後仍可閱讀。正文可限制行長，表格可自己捲動，整頁不得橫向溢出。**本輪不指定舊 880／960px 內容上限或主區 60% 高度**；應以實際 Kaosu 填寫／核對內容證明沒有壓窄、大片裝飾留白或按鈕被遮住。不能為了對齊來源的窄浮窗，把滿版工作區固定成中央一張 520px 窄卡。

### 2.5 Composer 與主要操作

採來源的**白色 composer 區、上邊界、白色 16px 圓角 textarea，以及黃色 48×48px 圓角送出按鈕**。文字框最小 48px、高度隨文字自然增加，約 112px 後內部捲動；桌面內距可沿來源 12px 上／16px 水平及下方，窄版保留安全區。[來源][S-INPUT-COMPOSER]、[基礎輸入上限][S-BASE-COMPOSER]

composer 與目前工作內容使用一致左右節奏；保留簡短鍵盤提示與必要的真實狀態說明。來源有白底輸入區及警示列，因此不再強制前輪「完全無底部區塊」或 128／144px 總高門檻；也不能照抄來源靜態警語，取代 Kaosu 的 writes gate、unknown、保存錯誤或 MES 時區。正常提示保持精簡，錯誤長文可自然增高。

黃色一般送出只送需求，保留 `send()`、IME、Enter／Shift+Enter、防重複、flush、未決鎖定與無模型出口。業務同意仍在唯一確認卡；卡片主要 CTA 可採同一品牌黃與深字，次要動作採白底／深藍文字。不得把聊天送出改成 confirm，也不得在摘要或浮動工具再複製第二顆業務同意。核對中 composer 是否可用，繼續由既有業務狀態決定。

### 2.6 摘要、查詢、歷程與確認卡

摘要／查詢／紀錄以來源次級畫面的白色標頭、淺灰底、白色卡片與明確返回動作呈現；不是另建第二個聊天室或另一份作業表單。工作中只留一組可辨認入口，缺項定位先收起覆蓋面板再聚焦主欄位。摘要保留一次對象、已填、缺項、保存狀態及階段，完整技術內容可放 details。

資料查詢保持唯讀，不自動換工單；需要帶入時明確選取，遵守未送文字、dirty、pending／unknown 與重新核對契約。關閉歷程／摘要回原頁與原焦點；面板 open／close 零 Guide mutation、零新 conversation。

確認卡用白卡／主題對應表面承載設備、工單、良不良數量、其他業務參數、所有受影響對象、期限與寫入限制。卡片動作與內容靠近、可自然捲動到達；不再用負 `bottom` 值猜測固定位置。成功、取消、被取代、明確拒絕與 unknown 有不同文字和合法下一步；不能僅用黃／綠／紅分辨。

### 2.7 模具時間與來源未涵蓋能力

模具上下四階段與清除仍由 `NEXT_ACTION` 及既有後端卡控；執行時間由 MES／伺服器記錄。畫面顯示唯讀時間或「執行時由 MES 記錄」，不能新增人工補登日期；排程可編輯的 `start_time` 不可移用到模具。時區來自既有 API 的 business timezone／time policy，不硬編碼原型的 UTC+07。[目標模具規則][T-MOLD]

排程與報工修改先讀原紀錄與正確識別，沿用 Guide.version、conversation revision、後端 state_digest 與 proposal.digest 的各自檢核。來源並無 Kaosu 的業務確認、版本保存、unknown、獨立同意與多工單影響；這些是目標能力，必須用來源視覺語言完整承載，不能因來源沒有便刪除或以假回執替代。
