## 1. R07 的問題定義與證據邊界

**建議列為 P2 的設計完成要求：收斂重複資訊層級，建立能辨認當前任務、輸入與下一步的作業畫面。** 使用者直接反映目前畫面難看；本規格把可改動的原因轉成可量測條件，不將主觀美感本身寫成後端 bug。

視覺診斷者依使用者提供的排程截圖（1885×867）估計：品牌／偏好、模組／身分、對話標題／工具、尚未選工單四層上方區帶合計約 285px；輸入與底部區塊約 213px。這是單張截圖的近似值，不是所有尺寸、語言或狀態的瀏覽器量測。現有原始碼則能證明以下結構：

| 已有證據 | 對使用者的影響 | 本輪設計決定 |
|---|---|---|
| `main.tsx:352、365、368` 同時保留四層資訊列。 | 先讀多層同義資訊，才到實際工作；畫面高度被工具與標題吃掉。 | 全域列與工作脈絡列收成兩層；常態合計不超過 112px。 |
| `main.tsx:372` 的三個 prompt 與 `:375` 的 GuidedFlow 起點並列。 | 同一件事有兩個入口，不清楚先按哪一組。 | 當前模組只有一組三個短任務入口；啟動任務後入口卡消失，才顯示按需工具。 |
| `conversation.css:6–7` 使用 820px 外層寬度，`styles.css:20–21` 的 messages／composer／proposal 又各有 48rem 限制。 | 作業卡、對話及輸入框不在同一條邊線。 | 三者共用一個約 880–960px 的內容寬度系統。 |
| 三份 CSS 依序覆寫控制項尺寸，包含 48→36→40／44px。 | 同一畫面的按鈕、字級與密度不一致，只改 tokens 不足以修好。 | 新工作區尺寸集中在 `conversation.css`，清理已被取代的桌面覆寫。 |
| `main.tsx:388` 側欄重複顯示情境，並直接呈現整包 snapshot。 | 摘要像另一張資料表，仍不能清楚回答做到哪裡、還缺什麼。 | 摘要保留一次對象、已填、缺項、保存狀態與階段；編輯及確認仍回主流程。 |

截圖不能證明鍵盤流程、模型準確度、正式交易或新人完成率；這些仍須依對應的功能與使用者驗收取得證據。

## 2. 確定的視覺方向

### 2.1 兩層緊湊頂部

第一層負責品牌、語言／主題及收合；第二層負責目前模組、可信身分與作業脈絡。標準桌面可採 56–64px＋44–48px，總高上限 112px。移除可見的「與助理對話」重複標題，保留有用途的區域名稱與 `aria-label`。尚未選工單是當前引導的內容，不另做一條全寬空白帶。

三模組切換、身分與權限說明、返回入口、語言及 light／dark／system 都須可到達。390px 時可把偏好收進有名稱的「更多」面板，把模組切換收成單一選單；不能以隱藏整個工作列換取高度達標。錯誤與重要執行狀態可增加必要內容高度，不得為守住數字而裁切。

### 2.2 單一內容軸

對話、目前問題、候選、欄位、確認卡及 composer 共用左右邊界。1366px 視窗的內容上限約 880px，1920px 視窗約 960px；較窄畫面依可用寬度縮排。390px 視窗左右各保留 16px。正文可另限制可讀行長，表格可在自己的容器內捲動，但不能讓頁面整體橫向溢出。

標準起始態以緊湊的標題、三個入口及輕量輸入形成一組，不在中間留出像另一個空面板的大洞。進入任務後，工作卡與 composer 採穩定的位置和一致寬度。常態主流程可見區高度至少為展開工作區視窗高度的 60%。長內容允許自然捲動；不以固定高度、縮小字體或裁切業務資訊達標。

### 2.3 Graphite 深色與暖白淺色

深色使用相對柔和的 graphite 底層、內容卡與 raised 表面三個層次；淺色使用暖白工作底、白色內容卡及略深的輔助表面。輸入框使用可辨認的表面和邊界，不能與整片背景混成一塊。避免純黑大底、整面高飽和色、裝飾性發光與漸層。

主要對話、欄位值與核對內容 16px，次要資訊 14px；主要任務標題桌面 24–28px、手機 22–24px。沿用現有中文字體與泰文字體來源，不新增外部字體、UI 套件或主題系統。

### 2.4 三個短任務入口只出現一組

排程起始態採「新增排程／查詢排程／調整排程」三個短入口；報工與上下模採同等語意的入口，對應既有操作能力。起始態不再同時顯示另一組長句 prompt，也不顯示摘要／資料／紀錄工具列。

**任務啟動後，三張入口卡被目前任務取代，工作標題右側才出現摘要／資料／紀錄。** 工具可放在第二層工作列或內容卡標題右側，不能再形成第三條全寬固定工具帶。這樣起始查詢卡與作業中的資料入口不會在同一畫面重複搶注意。

「任務已啟動」須從現有 Guide 步驟與查詢流程推導，不能只檢查 `guide.action` 是否非空；目前 `chooseAction('query')` 會保留空 action 並進入 target 步驟。唯讀查詢任務也應收起起始三卡，不能因此同時露出兩組入口。

三個入口是資訊分組，不是刪除功能。報工修改／刪除／改模穴／完工、排程新增／調整，以及模具上下模四階段／清除仍須從明確標示的次級「更多操作」到達。模具下一步仍由現有 `NEXT_ACTION` 及後端卡控決定，不能把「上模」或「下模」的短標籤當成新 action，不能自行略過階段。

查詢採現有唯讀路徑；資料查詢不自動更換目前工單。需要帶入另一筆時沿用明確選取、未送文字處理、pending／unknown 鎖定與重新核對。無模型時這組入口仍可接續人工流程，並與 R01 的可處理文字路徑一起驗收。

### 2.5 模具時間與修改示意的實作界線

上模與下模的執行時間沿用 MES／伺服器記錄，呈現為唯讀時間或「執行時由 MES 記錄」說明；不得要求人工補登，也不能將排程可編輯的 `start_time` 套用到模具操作。現有模具 action schema 僅接收 `schedule_id`，階段與時間仍由既有後端流程決定；詳見固定版本的 [action schema](https://github.com/WeYuTech/KaosuAiAgentTest/blob/3e1c7c002177f4bb16255cf3d26b840b82d7b4c7/app/domain.py#L43-L52)及[模具階段與時間處理](https://github.com/WeYuTech/KaosuAiAgentTest/blob/3e1c7c002177f4bb16255cf3d26b840b82d7b4c7/app/domain.py#L405-L444)。原型畫面的 `UTC+07:00` 是示範設定；正式顯示採既有 API 的 business timezone 與 time policy，不能以瀏覽器時間或原型常數改寫業務時間規則。

排程調整與報工修改在原型中明列為「修改示意」。正式實作先讀取原紀錄、正確的 `schedule_id`／`report_id` 及相關明細識別，沿用 Guide.version、conversation revision、state_digest 與 proposal.digest 各自的既有檢核，不把它們合成一個本機版本，也不新增原本不存在的資料庫版本欄位。原型欄位的預設值、修改動線或示範完成不能作為已讀取原紀錄、版本正確或正式修改成功的證據。

### 2.6 輕量 composer 與單一確認入口

composer 與工作卡同寬，只有一個可辨認的輸入表面；不要再用整片厚重底色、額外頁尾及多行裝飾提示包住它。桌面常態輸入＋必要提示＋頁尾合計不超過 128px，390px 鍵盤未開時不超過 144px。輸入本體初始約 64–80px，可增高至 160px 後內部捲動。低頻來源／回報資訊放有名稱的次要入口；MES 時區在相關時間與核對內容中保持可見。

composer 負責送需求，仍保留 Enter／Shift+Enter／IME 行為；業務同意只在唯一的確認卡執行。當前任務只有一個主 CTA：填寫時是下一步、核對時是同意、unknown 時是查核。送出圖示可以保留為輸入控件，但不能被做成第二個業務確認或與當前 CTA 同等的大型實心按鈕。

| 尚未選任務、Guide 載入完成 | 簡短任務標題、一組三個入口；不顯示空白對象帶。 | 選擇任務；入口組最多一個實心強調。 | 有需要才顯示文字需求入口；沒有摘要／資料／紀錄工具列。 |
| 載入或處理中 | 在當前位置顯示具體進度，如「正在讀取工單」；避免整頁空白或多個同義 spinner。 | 沿用既有在途鎖定，沒有第二個提交。 | 保留已輸入內容；讀取完成不能用晚到回覆覆蓋新任務。 |
| AI 未設定 | 簡短說明文字理解未開放，人工卡片仍可用。 | 直接從三個任務入口／操作卡繼續。 | 既有文字有可到達的清除或暫存出口；不能要求操作 disabled 輸入。依 R01 驗收。 |
| 選對象 | 顯示能區分設備、工單、品號、日期與執行識別的候選；選中樣式清楚。 | 明確選取正確對象。 | 唯讀查詢不自動換目標；切換遵守保存與 pending／unknown 限制。 |
| 填寫、dirty／saving | 當前問題與欄位為視覺中心；保存狀態以短文字靠近內容。 | 補齊／下一步，沿用既有鎖定。 | 摘要顯示已填、缺項與「尚未保存／保存中」；不能把 saving 當成已保存。 |
| 欄位 invalid | 原值保留，錯誤緊鄰欄位且能定位；不只用紅框。 | 修改有問題的值。 | 不新增另一組驗證規則；未通過不產卡，不因摘要收合遺失錯誤。 |
| 儲存 failed／conflict | 與當前欄位相鄰顯示保存失敗／版本衝突；保留本機值與伺服器核對入口。 | 讀回伺服器版本核對，後續選擇依現有流程。 | 不顯示永久 spinner；flush 未成功不送 proposal；不將「重試」改成盲目重送。 |
| pending、可確認 | 唯一確認卡顯示實際對象、良不良數量或其他業務明細、影響、期限。 | 「同意並寫入」或既有高影響確認文案。 | 返回修改／取消為次要動作；摘要無第二顆確認；保存、期限、寫入開關及獨立同意限制保留。 |
| pending 但寫入關閉／過期 | 原因就近顯示，仍能讀取完整核對內容；不把不可用按鈕當成唯一說明。 | 依既有契約取消、修改或重新核對；無同意寫入。 | 不改開關／期限；重新讀取不自動確認。 |
| 本機明確拒絕、待核對或待修正 | 顯示具體拒絕原因與目前核對狀態，不冒充後端 failed 或未知成功。 | 依 R03 修正後的讀回／返回修改路徑。 | 另一嘗試的 unknown 仍鎖定；R07 美化不能取代 R03 的 marker 修復。 |
| 提交中／unknown | 明示「正在送出」或「結果待核對」；原操作識別可直接取得。 | unknown 僅提供原 pid 的「查核執行結果」。 | composer、換工單與另開任務不能繞過；其他分頁原操作依 R04 提供恢復入口，無新 confirm／proposal。 |
| succeeded | 顯示經權威回覆確認的完成狀態、對象、實際變動與識別；workspace 更新失敗另說明。 | 查紀錄或明確開始下一筆，依既有流程。 | 不因查詢失敗改成業務失敗；不自動建立或同意下一筆。原型必須寫「示範回執」。 |
| cancelled／superseded | 取消與被取代明確區分；舊卡僅供回顧，不仍像有效待確認卡。 | 依當前 Guide 繼續修改或開始合法下一筆。 | 取消不能假裝報工成功；被取代的舊卡不得因折疊／開面板重新啟用。 |
| 登入／授權失效 | 顯示重新核對 MES 身分的明確入口；停止顯示前人的業務內容。 | 重新取得可信身分。 | 由 R02 清理資料與隔離晚到回覆；預設收合面板不能當成資料已清除。 |

## 5. 新增視覺驗收 V08–V16

以下全部是**待驗收條件**。像素與高度基準適用於展開工作區、100% 縮放、標準起始內容；200% 縮放、英泰長文、錯誤或多工單時，以完整可讀與可操作優先，允許自然增高及捲動，不能用裁切達標。對比數值是本提案的量測門檻，不構成整站 WCAG 合規聲明。

| ID | Given | When | Then／需留證據 |
|---|---|---|---|
| **V08 頂部層級** | 1366×768、1920×1080，三模組標準起始態 | 開啟／切換至各合法模組 | 頂部只有兩層固定資訊列，總高≤112px；沒有第三條對話標題或第四條未選工單帶。品牌、可信身分、三模組、偏好與收合可到達。390×844 用緊湊控件，長文及200%縮放不裁切。留尺寸與畫面。 |

## 6. 交付與實作順序

1. 以[可操作視覺原型](prototypes/emerald-visual-refresh.html)核對已提供路徑的外觀方向，並先閱讀[原型範圍與驗收紀錄](prototypes/emerald-visual-refresh.README.md)。修改流程是示意，模具僅展示上模開始；不要推論全部 action 已展示。原型只作呈現參考，不把合成資料、固定回答、示範身分或假回執複製進正式 app。
2. 在既有 React 架構實作 R07.1–R07.5，維持原 handler、狀態與權限；與 R01／R06 的起步修正協調，避免再次建立平行入口。
3. 依 R05 實作摘要投影與焦點定位，再完成 R07.6–R07.8；與 R02–R04 的身分／恢復修正共同驗證重要狀態。
4. 使用既有工具驗證必要功能，不新增套件、DB schema、後端執行器或通用流程框架。樣式測量與實際鍵盤操作要留證據，不能只以 build 成功或DOM快照宣告視覺完成。

正式實作 PR 至少留 1366×768、1920×1080、390×844 的起始／已填／確認卡／摘要開啟畫面，並記錄實際語言與主題；其他組合附驗收記錄。狀態測試使用可控延遲／錯誤，不使用正式業務資料。報告分開列出原型已展示、產品已驗證、未驗證與限制；沒有實測完整輔助科技及相關規範時，不宣稱完整無障礙或 WCAG 認證。原型的實測結果由 README 另行記錄，本規格不預先填入任何測試通過結果。
