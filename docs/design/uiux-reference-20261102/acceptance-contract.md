# UI／UX 範例與產品驗收契約（供新 Issue 整合）

本文件是新 Issue 的驗收建議，不代表 PR #30 已做下列產品實測。既有規格來源：[Issue #29](https://github.com/WeYuTech/KaosuAiAgentTest/issues/29)。新範例應補齊全系統畫面與時間性行為；沿用 #27／#29 的業務、權限、版本、期限、人工確認與預算保護。

## 1. 必須同時交付的三件事

1. **設計基準**：可操作的完整範例、重要狀態截圖、動畫示範及 scene manifest，凍結於 Git commit。場景控制列只能在範例展示外框，不混入產品畫面。
2. **產品實作**：相同資料、容器、語言及主題下，以真正產品元件與請求生命週期完成；不得複製範例的假資料、關鍵字路由或本機成功回覆進正式流程。
3. **產品驗收**：逐場景填寫來源 SHA、操作、結果、參考圖／產品圖、必要錄影與請求證據。範例自身通過 QA，不能替代產品通過。

## 2. 優先修正的觀感與 FLOW

- 首次送出任何有效問題後進入聊天室。顯示使用者訊息、AI 回覆／等待狀態及同一個持續可用的輸入框；首頁大標與常駐三捷徑不再佔據對話主區。沒有辨識到作業意圖時，回答問題或提出一個必要澄清，不強迫先選模組。
- 「你能幫我做什麼？」可用三個短句／可選入口回答能做什麼；「幫 MC37 報工」才進相應作業。已有機台、數量、日期等合法資訊直接帶入，不能先清空再問一次。
- 等待狀態必須有實際回饋。一般模式下 spinner 確實隨時間旋轉；長等待有簡短狀態及適用的停止／取消。reduced-motion 下可以靜止，但狀態文字、完成／失敗更新與可操作入口仍完整。
- 主要按鈕的位置和含義一致：選擇器是「套用」、編輯是「核對」、核對是具體業務動作；只有伺服器確認成功才能顯示完成。一般查詢的「停止」不等於撤回已送到 MES 的業務寫入。
- 版面重點是資訊順序、閱讀寬度、分組、動作位置與返回行為；不能只調圓角、字色或表單 padding 即宣稱完成。

## 4. Spinner 與轉場的可重現驗收方式

在**實際產品打包產物**載入的頁面，以隔離 HTTP fixture 延遲唯讀回應至少 2 秒。不得以範例或測試專用 spinner 替代產品元件。

1. 正常系統動態設定：錄下開始、持續等待、完成；查看實際 loader 的 `getAnimations()`／computed `animation-name`、duration、iteration 與 play state。至少三個不等距時間點（例如 0、170、410、680ms）取得 transform，證明等待期間角度真的改變。若用非 CSS 動畫，交付相應時間性證據。只驗證 class 名含 `animate-spin` 不算。
2. reduced-motion：明確記錄媒體設定；旋轉可停，但「查詢中」等文字與結果更新仍可辨識。不能拿 reduced-motion 測試來解釋一般設定下的靜止。
3. 覆蓋首頁／聊天室查詢、候選載入、資料頁重載、核對準備、提交／查核、設定與管理頁等**實際使用同一 loading primitive 的路徑**；共用元件可集中測時間性，路徑仍要檢查有無漏用／錯用／CSS 覆寫。
4. 開關選取器、換步、模式切換、對話新增與彈窗關閉各錄一段；檢查整頁閃爍、歷史重播、焦點失落、跳捲和重複可聚焦入口。靜態圖不能證明轉場合格。
5. 等待狀態不使用假進度百分比、不持續重排文字，也不反覆向 screen reader 播報每幀。明確進度只有後端可提供時才顯示。

可在新範例選定統一 motion tokens，例如一般進入 180–220ms、離開 120–160ms、spinner 900ms linear infinite；數字一旦由新範例確定，產品跟隨同一組 token。這些是設計值，不是宣稱所有裝置均達成的 FPS 或性能分數。

## 5. 視覺驗收不能自我放寬的規則

- 每筆證據固定 **design SHA、product SHA、scene ID、fixture ID、viewport、DPR、實際工作區尺寸、語言、主題、motion preference**。PR 最後一次 UI 變更後重跑受影響場景；舊圖不能混稱最新版本。
- 先並排看參考與產品，再列差異：資訊架構、相對尺寸／留白、字階、分組、按鈕位置、長資料、狀態、實際動作。允許必要業務欄位或字體光柵差異，但必須具體說明。
- 不得改 frozen reference、刪欄位／刪必要文字、縮小正常字級、裁掉問題區、把產品容器固定為範例高度、或調大允許像素差值來讓失敗變通過。必要設計變更另以有理由的變更紀錄建立新版本，保留原基準與差異。
- 自動 screenshot diff 可找偏移，但不能取代人工逐圖／逐錄影查看。任何實作 agent 均須實際開瀏覽器操作，不可只讀 JSX／CSS 後填「通過」。由另一 review agent 對證據做一次獨立檢查；其角色不能自動消除尚未滿足的條件。
- 狀態只用「通過／失敗／未測／不適用（理由）」；每個失敗與未測保留 blocker。測試總數、build 通過、overflow:false、已上線、模型預算0都不是視覺／UX 完成證據。
- 在 PR 摘要明列動態、reduced-motion、200%、iframe、三模組動作與 unknown 是否完成。任何必測項未完成，不標成整體 UI／UX 驗收通過、不關閉 Issue。
- 本 Issue 的驗收門檻是工程交付條件，無需每一小步再請使用者批准；但尚未實測的正式站不可宣稱驗收完成。

## 6. 最小證據目錄建議

`docs/evidence/<issue>/manifest.json` 記錄以上版本與環境，`acceptance.md` 逐 AC ID 填結果，`screens/` 存成對圖，`videos/` 存連續操作片段，`requests/` 存遮蔽過的請求證據。先完成首頁首問／查詢動態及一個完整雙模式報工，再依同套元件拓展其餘 scene；每個新增 surface 都先對照再往下一頁，不等全部改完才第一次看畫面。
