# 決策：沿用業務來源，新增可確認的交易閘道

日期：2026-10-30

## 背景

現行 MES 已有查詢函式、畫面、API 與資料庫 Trigger。逐支核對後，報工部分 API 沒有交易，內部 SQL 失敗仍可能回傳成功；完工和下模還有跨工單連動。直接讓模型呼叫舊 API 不能確保確認卡內容與實際結果一致。

## 決策

新增 AI 協調後端，將查詢、草稿、確認與執行分開。查詢沿用已核對的固定 TVF／查詢來源；有資料變動的命令採固定白名單、參數化 SQL、交易、版本檢查、冪等識別碼、讀回驗證與同交易稽核。

排程明細的執行歷程生成繼續使用原資料庫 Trigger，不能另寫一套假設的正式同步邏輯。原規則與新增防護分開記錄，危險的原始缺陷不照抄。

模型僅能查詢及準備草稿。所有寫入以可信身分確認後執行，部署預設關閉正式寫入。隔離 SQLite 回放、獨立 SQL Server 驗收與正式環境三種證據不可混稱。

## 影響

需要維護小型明確的命令契約與 SQL 來源盤點；收益是可驗證交易結果及追溯實際欄位異動。舊系統版本、Trigger 或表結構改變時，必須重新跑契約與 SQL 驗收，不能只更新提示詞。
