# ADR 003：以原 MES 伺服器工作階段登錄表驗證持續身分

日期：2026-10-30。狀態：採用；取代「Session Token 必須等於 SEC_USER.REFRESH_TOKEN」作為正式嵌入環境的身分契約。

## 問題與證據

單獨登入後的測試會通過舊比對，但瀏覽原報工頁、執行既有查詢後會失敗。原部署程式的 `SECFun_H5.VeriftyAndGetTokenObj`（反編譯 247–280 行）驗證成功後重新生成 Token；`DBQuery_H5.GetReader`（183–198 行）呼叫此流程，`SessionHelper.UpdateToken`（24 行）把新 Key 存回 Session。`SEC_USER.REFRESH_TOKEN` 僅由登入流程更新，因此兩個 Token 不再相同。

原 `H5_LoginController.Post` 登入成功後將 `RegisterSession` 產生的 GUID 寫入伺服器 `Session["SessionId"]`（171 行），對應 `SEC_APP_SESSION_REGISTRY.SESSION_ID` 的 USER_ID。登出會刪除工作階段登錄與伺服器 SessionId。這提供不依賴持續輪替 Token 的可信關聯。

## 決策

在原 KSS_MES 同一 ASP.NET 應用加入單一 `AiAgentSession.ashx`，實作 `IReadOnlySessionState`。僅允許 loopback GET，驗證伺服器 Session 具有有效 Key、非零 GUID 與未過期時間，只回 GUID 與到期時間。不接受請求的帳號／身分，不回傳 Token，不更新 Session 或業務資料。

Python 使用固定本機端點轉送指定 Session Cookie，再以參數化 SQL 將 GUID 對應未刪除的登錄列與啟用使用者，要求唯一結果。模組 allowlist、知識審核權限與短效內部簽章維持原有界線。正式設定固定為 `session-registry-v1`，橋接錯誤不降級回 Token 或前端身分。

## 驗證與代價

新增端點需與原 MES 應用一起保存，後續整站重新發行時不能遺漏。IIS 之外的部署不可直接沿用 loopback 假設，需另行建立受保護的內部通道。

公開 HTTP 測試涵蓋 Token 輪替後仍認得同一工作階段、缺少／錯誤 GUID、過期、刪除登錄、停用使用者及橋接拒絕。現場已驗證 ASP.NET 可編譯、未登入本機請求為 401、外部直接請求為 403；持續嵌入查詢另記於 IIS 驗收。
